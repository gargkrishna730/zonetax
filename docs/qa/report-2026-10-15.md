# Data validation and region bug — 2026-10-15

Triggered by a report that a `us-west-2` install displayed `us-east-1`. Scope: validate the
data after 8 days of continuous running, and review the codebase for related defects.

Environment: a real 3-AZ EKS test cluster, 5 nodes, collector up 8d (Helm rev 15), history
persisted to a PVC.

## Bug 1 (critical): every install reported the same hard-coded region

`cmd/collector/main.go` read:

```go
Cloud:  envOr("CLOUD_PROVIDER", "aws"),
Region: envOr("CLOUD_REGION", "us-east-1"),
```

and **neither variable was referenced anywhere in the Helm chart**. Confirmed on the live
collector, whose only env vars were `GOMEMLIMIT` and `HISTORY_FILE`. So `CLOUD_REGION` was never
set by any Helm install and every deployment fell back to `us-east-1` regardless of where it ran.

Impact:

- The dashboard displayed the wrong region.
- The pricing table was queried with the wrong region key. Today every AWS region in the table
  happens to be $0.01/GB, so the dollar figures were still right — this was a display and
  correctness-of-lookup bug, not (yet) a mispricing one. It would have become a real mispricing
  bug the moment a region with a different rate was added.

Fix: new `internal/clouddetect` package infers cloud and region from `spec.providerID` and the
standard `topology.kubernetes.io/{region,zone}` node labels, which the collector's RBAC already
allowed it to read. Resolution order is now:

1. `CLOUD_PROVIDER` / `CLOUD_REGION` (explicit override wins, and logs a warning when it
   disagrees with detection)
2. auto-detection
3. cloud default with an **empty** region

Step 3 deliberately does not invent a region: an unknown region is reported as unknown and
priced at the cloud-level default rate. Claiming a specific wrong region is worse than admitting
it isn't known. Per-node majority voting means one odd node can't move the whole cluster's
pricing.

`cloud.provider` / `cloud.region` are now exposed in `values.yaml`, both empty by default
(= auto-detect). The generated manifests are unchanged by default, since empty values render no
env vars.

Verified against the live cluster, not just fakes (`internal/clouddetect/live_test.go`, build
tag `livecluster`):

```
context=<test cluster> cloud="aws" region="us-east-1" nodes=5 zones=[us-east-1a us-east-1b us-east-1c]
```

The same code path in us-west-2 now yields `us-west-2`.

## Bug 2: partial measurement was invisible

One agent pod had been `Pending` for 4d5h (`Insufficient memory`), so
1 of 5 nodes was never measured — but `/api/v1/costs` exposed no coverage information at all.
A cluster with a dead agent looked identical to a cluster with no cross-AZ traffic, silently
under-reporting cost. This directly violates the project rule that missing data must be reported
as missing, never as $0.

Fix: `costengine.Coverage` (`nodes_total`, `agents_scraped`, `agents_failed`,
`unmeasured_nodes`, `complete`), populated each cycle by comparing the node list against agents
that actually returned metrics, surfaced in the API response, and logged as
`PARTIAL COVERAGE` when incomplete. Failed scrapes count as gaps too, not just missing pods.

Note this is also why ZoneTax reads low against the AWS bill: the unmeasured node's traffic was
never counted. Coverage now makes that visible rather than leaving it as an unexplained gap.

## Bug 3: two tests had rotted and were failing on `main`

`TestStore_RestartKeepsHistoryAndMarksDowntime` and `TestStore_DowntimeMidHourIsPartial` were
failing **before** any change in this session (confirmed by stashing). They anchored to a
hard-coded `2026-10-01`, which had aged past the 7-day retention window, so `loadHistory`
correctly evicted the buckets and the assertions failed. The code was right; the tests were
time-dependent. Fixed with a `recentBase(hoursAgo)` helper anchored to now.

## Still open

- The `Pending` agent still can't schedule (node genuinely out of memory). `agent.priorityClassName`
  exists to fix this but is unset on the test cluster; coverage now reports the gap either way.
- GCP pricing is not in the table yet. GCP charges cross-zone **sender-side only** ($0.01/GiB),
  unlike AWS's both-directions billing, so the hard-coded `crossAZBillingMultiplier = 2` and
  `bytesPerGB = 1e9` (GCP bills per GiB) must both become per-cloud before GCP is claimed.

## Post-deploy verification (same day, Helm rev 16)

Both fixes confirmed running in-cluster, not just in tests. Collector logs on startup:

```
detected cloud="aws" region="us-east-1" across 5 node(s), zones=[us-east-1a us-east-1b us-east-1c]
pricing cross-AZ traffic as cloud="aws" region="us-east-1"
collector: PARTIAL COVERAGE: 4/5 nodes measured, unmeasured=[<node>]
```

The region now comes from live node labels rather than the hard-coded default, and the
previously-silent measurement gap is reported. `/api/v1/costs`:

```json
"region": "us-east-1",
"coverage": {"nodes_total": 5, "nodes_measured": 4, "agents_failed": 0,
             "complete": false, "unmeasured_nodes": ["<node>"]}
```

Totals arithmetic still exact after the upgrade (13.8189 GB x $0.02 = $0.27638, matches
reported). History survived the rollout via the PVC: 169/169 buckets retained, `history_start`
unchanged at 7 days back.

### Ruling out a false positive

The test cluster is itself in `us-east-1` — the same value as the old hard-coded default — so
"the API says us-east-1" alone cannot distinguish real detection from falling back again. Four
checks together close that gap:

1. **The string is gone.** `grep us-east-1 cmd/collector/main.go` returns nothing. There is no
   hard-coded region left to fall back to.
2. **The fallback now yields empty, not a region.** With no labels and no env var,
   `resolveCloudRegion` logs `region=""` and warns that the region is unknown
   (`TestResolveCloudRegionUnknownStaysEmpty`).
3. **Detection reports data only the cluster could supply.** With `CLOUD_REGION` absent from the
   pod (verified via `kubectl get deploy -o jsonpath` over the container's env — the exact
   pre-fix condition that caused the bug), the collector still logs the region *and the three
   zone names*. A fallback constant cannot produce the zone list.
4. **A non-default region flows end to end.** `--set cloud.region=us-west-2` put
   `CLOUD_REGION=us-west-2` into the pod env (previously no such var existed at all), the
   collector logged the override warning against the detected value, and `/api/v1/costs`
   returned `"region": "us-west-2"`. This exercises the chart plumbing that was the actual root
   cause.

`internal/clouddetect/relabel_live_test.go` additionally asserts the detected region equals what
the node labels independently say, so a hard-coded return value would fail the test rather than
pass it by coincidence.

Across three consecutive rollouts (rev 16, 17, 18) history remained at 169 buckets with an
unchanged `history_start`, and totals arithmetic stayed exact
(13.8235 GB x $0.02 = $0.27647 = reported).

## Full config audit (follow-up)

The region bug raised an obvious question: is anything *else* read from the environment but
never set by the chart? Enumerated every env var the binaries read and diffed against what the
templates set.

Read by code but **not** set by the chart: `AGENT_NAMESPACE`, `AGENT_LABEL_SELECTOR`,
`SCRAPE_INTERVAL_SECONDS`, `SCRAPE_TIMEOUT_SECONDS`.

**None is a second instance of the same bug**, and the distinction matters. The region default
was dangerous because it was a *specific factual assertion about the cluster* that was silently
false. These are different:

- `AGENT_NAMESPACE` falls back to reading
  `/var/run/secrets/kubernetes.io/serviceaccount/namespace`, i.e. the real namespace — dynamic
  and self-correcting, not a guess.
- `AGENT_LABEL_SELECTOR` defaults to `app.kubernetes.io/component=agent`, which matches the
  labels the chart actually applies. Verified against the live cluster: the selector returns all
  5 agent pods.
- `SCRAPE_INTERVAL_SECONDS` / `SCRAPE_TIMEOUT_SECONDS` were hard-coded at 30s/5s, but the API
  *reports the value actually in use* (`scrape_interval_seconds`) rather than asserting a
  possibly-wrong one. Confirmed live: logs showed `interval=30s` and the API agreed.

So these were tunability gaps rather than wrong data. `collector.scrapeIntervalSeconds` and
`collector.scrapeTimeoutSeconds` are now exposed anyway (defaults unchanged at 30/5, so
behaviour is identical), since the scrape interval is the data-freshness bound and operators of
large clusters have a legitimate reason to raise it.

Verified end to end rather than by inspection: `--set collector.scrapeIntervalSeconds=20`
produced `interval=20s` in the collector log and `"scrape_interval_seconds": 20` in the API
(rev 19), then reverted to 30s (rev 20). `NODE_NAME` is set via `fieldRef` and the agent warns
loudly if it is ever empty, so it can't silently mis-attribute traffic.
